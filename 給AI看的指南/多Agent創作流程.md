# 多 Agent 創作流程（共同規則；作者 2026-09-28 定為所有創作內容通用）

> **適用範圍：** 凡是要**生出或改寫遊戲文本**的活——高難度檢定新戲、蝴蝶效應分支、回音一句、人物線與事件的新劇本、審稿單改稿——派 agent 時都照本檔的形狀跑。各用途只差「讀哪份規則、跑哪支腳本、起草的三個取向差在哪、提案檔放哪、定稿另套用什麼」，**全列在第九節對照表**。
> **規則本身**（那場戲該怎麼寫）不在本檔：文風看三份必讀指南；高難度檢定看 `高難度檢定走向指南.md`；蝴蝶效應看 `劇情/蝴蝶效應_素材與設計.md` §一、§三、§八；回音看同檔 §九；人物線看該角色資料夾的設計端與 `@角色設定/`。本檔只管「誰做什麼、依什麼順序」。
> **執行工具：** Workflow 腳本，放 `.claude/wf/`。母版 `hard-check-v2.js`（起草到提案檔）、收尾 `finalize-and-convert.js`（作者挑版之後）。新用途照母版改一支，情境包的內容換成那個用途的規則；**每一支都要有 3b 邏輯審那一步**。
> - 母版必填參數：`args.date`，填當天日期。選填：`args.only` 只跑某幾場；`args.have` 標出哪些場的情境包或起草稿已存在、可以沿用。
>
> ⚠ **跨機注意：** `.claude/` 整個資料夾未進 git（見本檔第八節）。到另一台電腦要先確認腳本在。
> **沿革：** 本檔原名 `高難度檢定_多agent流程.md`（2026-09-26 第二級，只管高難度檢定）；2026-09-28 作者定為共同規則、改名，舊路徑的引用都已改過。高難度檢定那一套的細節收進第九節，內容不變。

## 一、分工（一場戲十名 agent：三起草、三審修、三邏輯審、一終審；加一名素材範圍共用的整理）

| 步驟 | 人數 | 推理強度 | 產出 |
| :--- | :--- | :--- | :--- |
| 整理情境 | 一個素材範圍一名（通常＝一個箱庭或一份事件檔） | xhigh | 情境包檔案 ＋ 一頁摘要 |
| 起草 | 每場三名，各寫一版 | xhigh | `draft-甲／乙／丙.md` |
| 審修 | 每場三名，一人負責一版 | **max** | `revised-甲／乙／丙.md` |
| **邏輯審**（2026-09-28 作者要求加，排在審修之後、終審之前） | 一版一名 | **max** | 只看事理：誰知道什麼、先後因果、人在哪、東西去哪、旁白與台詞不打架、分支前提、前後場接口；直接修，記「邏輯審」 |
| 終審兼寫檔 | 每場一名 | **max** | 提案檔（位置依用途，見第九節） |

- **模型一律 Opus 5.5。** 腳本裡寫死 model，不靠繼承主對話的模型。
- **推理強度（作者 2026-09-27 定）：全部最低 xhigh；審修、邏輯審與終審是品質關卡，用 max。** 原因：文本品質不穩。第六節的實測數字是 medium／high 時量的，現在會更慢、更花。
- **所有場次同時跑，不分組排隊。** 同一素材範圍的幾場戲等同一份情境包。
- **暫存檔放在 scratchpad 的 `hc/<素材範圍或場>/` 底下，不進專案。**
- **派出去的 agent 一律寫明 git 只准讀。** 2026-09-27 有一名 agent 用 `git stash` 還原時把 71 個 LF 檔寫成 CRLF，收拾了一整批。
- **跑完只有提案檔有改動**：`Json/`、回讀稿、創作稿、角色檔、指南都不動。改字一律等作者挑版、定稿之後走第三節。

## 二、各步驟做什麼

### 1. 整理情境

把後面的人需要的東西**逐字抄**成一份情境包 `hc/<素材範圍>/packet.md`，**只抄事實、不提改法**。內容有：

1. 這個用途的規則原文（走向指南相關節、素材與設計檔的規格、人物線設計端——照第九節）。
2. 每場掛點前十格到接回點後十格的原文（新劇本沒有掛點的，抄前一場的結尾與後一場的開頭）。
3. JSON 的連線與 parent。
4. 每條會播到掛點的來路與條件，含有娜娜／沒娜娜、隊上有誰。
5. 既有的固定句（例：骰子亮的句子）。
6. 每個出場角色在本素材範圍說過的每一句話（`python 給AI看的指南/既有台詞.py <角色>`）。
7. 設定檔段落。
8. 兌現處候選（未卜、回音那類要往後接的）。
9. **〈指南摘錄〉**：把三份必讀指南和各轉換規則裡這場戲用得到的節**逐字抄**進來。固定要有：
   - 文本創作指南：第零層、0.2.3、0.6、2.1a。
   - 世界觀：第八節。
   - 武俠文風創作指南：**〈零、常犯十條〉整節（放情境包最前面，2026-09-28 作者要求）**、旁白卡、主角卡、出場角色聲口卡、7.1a–7.1c、7.3、自檢清單。
   - 饕餮廢案清單（`@角色設定/饕餮.md` 第十節）。
   - 轉成json指南：§1 詞表、§4.2。
   - 立繪指令轉換規則：可用格號。
   - 用到擲骰的加擲骰指令轉換規則（四段寫法與 ID 對照表）；用到戰鬥、音樂、畫面的加對應那份轉換規則。

回傳給下游的只有一頁摘要，細節都在檔案裡。

### 2. 起草（三名，各一個取向）

- 三個取向差在哪，各用途不同，見第九節；腳本逐場把取向和要避開的東西寫進情境包。
- > ⚠ **作者准的例外（作者 2026-09-26 准，只限本流程的起草步驟）：起草者只讀情境包，視同讀過 `CLAUDE.md` 規定必讀的三份指南。** 因為情境包第 9 項已把用得到的節逐字抄進來。**其他步驟、其他工作照 `CLAUDE.md`。** 別的 agent 讀到 `CLAUDE.md` 的必讀規定時，以此條為准許的例外，兩邊不矛盾。
- 起草只管寫戲，**不回 JSON 查連線**，連線交給審修。只有情境包缺了非要不可的東西才回原檔讀那一段，並記一筆。
- 寫完只跑一次 `文風節奏檢查.py`，照報告修一次就交。
- 稿子的固定結構：**取向、（秘密）、（檢定）、掛點與接回、讀的條件、寫的指令、戲、兌現處、起草者自檢。** 括號裡的沒有就不寫。

### 3. 審修（一人一版）

- 逐項查本場的檢查項（高難度檢定是八項：連線、來路、既有格有沒有被改、留白、擲骰結構、獎勵與代價、選項格式、`Description` 詞表；其他用途拿掉不適用的、加上第九節列的），回原 JSON 和總覽稿查證。
- 逐句查文風規矩，口吻對照情境包裡的既有句。
- 另外依用途加查（見第九節）。
- 能修的直接修，**但要守住那一版的取向，不能修成別版**。不該由 AI 定的留空白，記進〈待作者定〉。
- **旁白逐格表（2026-09-28 作者要求）：** 每一個旁白格一行：格名｜第 3 條（判語、心事、替玩家下感受）過或改｜第 7 條（造景細節、精確數目、動作鏈超過兩拍、收尾巧句）過或改｜改了什麼。不准整段打勾，一格一格重讀。`文風節奏檢查.py` 列出的「旁白卡候選」每一條都要在表裡有交代。
- 每一處改動記進〈審修紀錄〉：第幾格、原句、新句、依哪條規矩。
- 修完跑 `文風節奏檢查.py`；用途有格式檢查腳本的一併跑（第四節）。
- 選一個人審三版不會更省 token，而且比較慢，所以採一人一版。

### 3b. 邏輯審（一人一版；2026-09-28 作者要求加，排在審修之後、終審之前，推理強度 max）

> **為什麼要有這一步：** 檀石槐線〈老兵的委託〉裡，主角前一句已經喊了「老丈」，旁白後一句才「認出」他是那個老兵，等於認了兩次。這一句穿過了審修、終審、連貫檢查三層都沒被抓到，因為那三層的清單管的是規矩、格式、口吻、條件寫法、共同事實，**沒有人專門看事理通不通**。作者 2026-09-28 問「現在有沒有 agent 是處理這種邏輯的問題」，答案是沒有，所以補上。

- **只看六件事，不管規矩、格式、口吻**（那些審修管過了）：
  1. **誰知道什麼：** 每一格說話的人、主角、旁白此刻知道的事，是不是前面已經看見或聽見的。沒看見的不能認出，沒聽見的不能回答，同一件事不能認第二次、不能講第二次。
  2. **先後因果：** 先看見才能叫人、先問才有答、先做才有結果；轉場前後的時辰、天色、地點接得上；人在哪、誰在場，前後一致。
  3. **東西的去向：** 拿出來的東西有收回或交代（碗、杖、弓、錢、旗）；沒有憑空多出來的東西。
  4. **旁白和台詞不打架：** 旁白不重講台詞剛講的事，也不比台詞晚一步才交代台詞已經用到的事實；選項文字跟後面的戲對得上。
  5. **每條分支的前提在那條路上真的成立：** 寫「認識某人」的那條，玩家在那條路上真的見過他；寫「拿到某物」的那條，前面真的給過。
  6. **前後場的接口：** 這一場開頭假定的事，前一場真的演過；這一場結尾留下的狀態，後一場用得上。
- 先讀情境包裡這一場的現行拍子（箱庭則讀施工圖與前一場的對話），再逐格讀那一版的審修稿。
- 能修就直接修進同一份檔（對話置頂的稿，第一節與第二節同步改），修完那一格仍守該版取向與文風規矩；拿不準是不是問題的列出來不改。
- 每一處改動記進〈審修紀錄〉，標「邏輯審」；該作者定的記進〈待作者定〉。修完跑一次 `文風節奏檢查.py`。
- **現有腳本都已加這一步**（`hard-check-v2.js`、`butterfly-shidan.js`、`butterfly-fangqi.js`、`butterfly-tanshihuai.js`、`butterfly-tanshihuai-box.js`）；**`finalize-and-convert.js` 的定稿人與複核清單各加了同一條**（定稿人合幾份時，接口那幾格特別看）。**以後新腳本一律要有。**
- 回傳：`file`、`issues`（每筆 where、problem、fix、fixed）、`summary`。終審拿到的是邏輯審過的稿。

### 4. 終審兼寫檔

- 讀完三版審修、邏輯審過的稿，再挑一次錯。重點放在審修最容易漏的地方：每條來路接不接得通、擲骰或選單結構、獎勵指令、三版是不是三個真的不同的選擇。
- 標一版建議版，附一句理由。
- 寫提案檔（位置依用途，見第九節）：
  - 第一行寫 `# 〈場〉　〈用途〉提案（〈分類〉）｜創作稿／提案，尚未進 JSON`。
  - **對話文字放置頂**（作者 2026-09-28 裁示，之後所有提案檔、定稿檔都這樣排）：純對話、一層一層、分岔 ▶、選項 ◆，作者只讀這一段；**給 AI 看的東西全放後面**（節首表、逐格 actorID／Sequence／Conditions／Script／Description、待作者定、審修紀錄、自檢）。三版提案檔＝三段對話在前、三段逐格在後。
  - 引用區塊寫掛點與接回、建議版、待作者填。
  - 三版各一節，每節含戲、兌現處、審修紀錄。
  - 最後是合併去重的〈待作者定〉和〈審修摘要〉。
- 跑檢查腳本，確認**只動了提案檔**，沒動 `Json/`、回讀稿、規則檔。

## 三、作者挑版之後：定稿

> **定稿人也要把 3b 的六件事過一遍**（2026-09-28 起），合幾份提案成一場時，接口那幾格特別看；複核清單同樣有這一條。

> **2026-09-27 起可用腳本跑這一步：** `.claude/wf/finalize-and-convert.js`（作者裁示寫進 `args.jobs`，每份提案檔一筆：選定版、對應 JSON、作者裁示逐條、設計端連帶），每份提案檔一名定稿、一名轉 JSON、一名獨立複核，三步都是 max，同一份 JSON 的幾份依序寫。手動派單一 agent 的做法仍可用，但吃不到 max。

作者給出「選哪版」（有檢定的加「難度多少」）後，每場一名 agent **只改那一份提案檔**。

- 在檔頭引用區塊之後新增 `## ✅ 定稿（作者〈日期〉選定：版〈X〉〔，〈檢定〉〈難度〉〕）`，放選定版改好的完整戲，對話置頂；之後轉 JSON 以這一節為準。
- 定稿時套用當下已定的規則；各用途另要套用的列在第九節。
- 其他台詞不動。非改不可的，節末〈定稿改動〉逐條記原句、新句、理由。
- 原三版留在後面，節標題加「（選定前原稿）」或「（未選，留存）」。
- 〈待作者定〉改寫成只剩定稿版仍有效的事。
- 定稿節跑檢查腳本**必須乾淨**。未選各版裡的舊句被報警告可以不管。
- 之後才是轉 JSON：續號、補 `zh_CN`、跑 `json順序檢查.py`、走 `Unity對話同步流程.md`、回讀進該場的總覽稿、更新該用途的登記表（走向指南第十一節、雲端追蹤頁的 stage 等）。提案檔在合併、轉 JSON 之後移進 `劇情/舊創作稿/`。

## 四、檢查腳本

- `給AI看的指南/文風節奏檢查.py`：所有用途都跑。抓碎句、超長台詞、em7 與表情特效用量。
- `給AI看的指南/json順序檢查.py`：轉 JSON 之後跑。陣列順序、`entryID` 連號、`Description` 詞表。
- `給AI看的指南/高難度檢定檢查.py`（2026-09-26 新寫，只有高難度檢定跑；別的用途裡有擲骰的也可以借用擲骰那幾項），檢查以下各項：
  - 選項格式與三句題語，以及題語和分類對不對得上。
  - 檢定標籤是不是遊戲既有的。
  - 擲骰四段包裝、手動檢定、`FeatID`、難度格式。
  - `IsPassDice` 成敗兩邊齊不齊。
  - 變數、任務號、教學 ID 是既有的，或留 `＿＿`，或是作者定名的。作者定名的變數寫在腳本的 `AUTHOR_VARS`，目前只有 `IsHidden1`（新號要一併加進去）。
  - `SetFlag`、`title` 禁用。
  - `Description` 在不在詞表內。
  - em7 密度、`[/em7]` 後的標點。
  - 硬紅線詞；骰子格不寫燙熱顫震。
  - 骰子亮是不是固定句。
- ⚠ 腳本已知的小毛病：說明文字裡貼了擲骰指令原文，會被誤判成擲骰格，要改成白話描述。
- ⚠ 腳本尚未檢查的兩條（2026-09-26 新規，待補）：轉機選單有沒有「離開」；轉機不過那格有沒有 `ModifyData(Coin,-200)`。

## 五、跑的時候要注意

- **額度：** 五小時額度用完時，正在跑的 agent 全部失敗、回傳空值，不會自己重試。要看 transcript 資料夾裡的 `journal.jsonl` 有沒有 `failed`，額度恢復後再續跑。
- **續跑是前綴比對：** `resumeFromRunId` 照 agent 呼叫順序一條一條比，第一個不同的呼叫之後全部重跑。改腳本加新場次會打掉舊場次的快取。要保住成果，把已完成的情境包和起草稿存檔，用 `args.have` 沿用。
- **跑之前先鎖住規則：** 開跑後才改指南，會讓整批重做。
